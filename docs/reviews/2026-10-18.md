items are kept short. Fixes in `engine/` need your approval under the project rules; each one is tagged

### 1.1 `ctf-checker` trusts a self-asserted user. Medium–High for competitive CTF · Verified
- **Where:** `modules/ctf-range/ctf-checker/checker.py:125-138` (`validate_check`) and the `/reset`/`/check` handlers at
  about lines 370-393; `modules/ctf-range/terminal/dojo-reset.py:30` sends `$USER`. The docstring at lines 3-11 says this
  is a deliberate choice.
- **What happens:** the request names the user, and the only check is that the name is on the roster. The rate limit
  is keyed on the same claimed name, so it doesn't slow a student who cycles through victims.
- **Scenario:** `curl -d '{"user":"student05","target":"policy-bypass"}' ctf-checker:9200/reset` sends student05's
  patched box back to the vulnerable base image in ctf-defend, where fixes are scored. `/check` also shows another
  student's verdict.
- **Related:** `ctf-flags/service.py` also takes `user` from the caller, and the same flag can be submitted
  repeatedly. Its own comment accepts this, but combined with the checker it lets a student credit any name with a
  flag they have.
- **Fix:** tie identity to something the caller can't choose. The repo already has two good patterns:
  - a per-user key derived from the seed, as `dns-gate` does with `dns_key`;
  - a root broker that reads the caller's uid from the socket (SO_PEERCRED), as in `dojo-cloud/terminal/dojo-broker.py`
    and the openbao broker.

  See §3.3 for doing this once for every module.

### 1.2 The gateway forwards dojo cookies to every upstream. Medium · Verified
- **Where:** `engine/gateway/Caddyfile` (no `header_up Cookie` rewrite anywhere) and the upstream template in
  `engine/allocator/render_extensions.py`.
- **What happens:** the facilitator's `dojo_login` cookie and the student's `dojo_session` both go to Forgejo, every
  extension route, `/admin/watch` and the IDE and terminal ports.
- **Scenario:** a student gets control of an extension upstream, such as app-host or runner output (the threat model
  behind FIND-16). They wait for the facilitator to open that route or an `/admin` tab, and capture the cookie. It is
  stateless and valid for 12 h, so replaying it gives full facilitator access. That undoes the per-upstream token
  work from FIND-16.
- **Fix:** strip the dojo cookies in each upstream block and in the gate template, for example
  `header_up Cookie "(^|;\s*)dojo_(login|session|gate)=[^;]*" ""`. Check that Forgejo's own cookie still passes
  through. **[engine]**

### 1.3 The login rate limit doesn't stop guessing. Medium/Low · Verified
- **Where:** `engine/allocator/api.py:308-330` (`handle_login`) and `accounts.py` (`LoginGuard`).
- **What happens:** `check_login` runs first, and `LOGIN_GUARD.blocked` is only consulted after a wrong password. A
  blocked address can keep guessing, and the right password still succeeds. The `LoginGuard` docstring says "429
  before any password is compared", but the code doesn't do that. The `--pass` gate has the same gap: Caddy validates
  the cookie itself, and the allocator only counts failures.
- **When it matters:** only with short or known secrets, such as `--env home` or a short `--pass` code.
  `--env live`'s 48-bit generated passwords are fine either way.
- **Fix:** after N failures from an address, slow every attempt from it, right or wrong, or block per username. At
  minimum, fix the misleading docstring. **[engine]**

### 1.4 Class-wide CTF tokens sit in student-editable CI. Medium · Reported (exfiltration unverified)
- **Where:** `workshops/ctf-defend/FACILITATOR.md:135`; token comments in `modules/ctf-range/module.env:60,78`.
- **What happens:** `CTF_BUILD_TOKEN` and `CTF_CONTROL_TOKEN` are Actions secrets in each student's repo, and the
  workflow files live in that repo. A student can edit a workflow to print them, then from `runner_net`:
  - POST `ctf-controller:9000/redeploy` for any user;
  - call `/gate`;
  - read `/slots` and `/schedule`.
- **Fix:** run the platform step from a workflow source students can't edit, or use per-user tokens
  (HMAC(seed, user)) that only work on that user's own slot.
- **Also:** four CTF packs hard-code `CTF_CONTROL_TOKEN=dev-ctf-cont…` in `workshop.env` (lines 29-30 of
  ctf-access, ctf-server-trust, ctf-secrets-config and ctf-trust-chain). ctf-defend derives its token from
  `GATEWAY_TOKEN`; use that derivation everywhere.

### 1.5 With no seed, flags and student secrets fall back to guessable values. Medium (config) · Reported
- **Where:** `modules/ctf-range/ctf-flags/flags.py:34` and `ctf-controller/flags.py` produce
  `flag{<challenge>-dev-<user>}`. `engine/allocator/dojo_secret.py` falls back to `FALLBACK_PASSWORD = "student123"`.
  `engine/dojo/start.py:454` only warns when the seed is missing.
- **Fix:** refuse a non-`--test` start (or at least `--env live`) when `STUDENT_PASSWORD_SEED` is empty. **[engine]**

### 1.6 Lower-severity items
- **Low · Reported:** `render_extensions.py:63-64` doesn't reserve `/login`, `/logout`, `/session-check`,
  `/gate-fail` or `/_gate`. A manifest could claim them: Caddy order hides `/login`, and taking over the others needs a
  login first. Add them to `ENGINE_PREFIXES`/`ENGINE_EXACT`. **[engine]**
- **Low · Reported:** the `@login`, `@gateprobe_bad` and `@gatebad` Caddy blocks set `X-Gateway-Token` but pass the
  client's own `X-Auth-User` through. There's no exploit today, because those handlers don't call
  `resolve_identity`. Add `header_up -X-Auth-User` there so a future handler can't trip on it. **[engine]**
- **Low · Reported, design:** everything runs on one origin (`/git`, `/ide`, `/admin`, extensions), so the
  facilitator's `X-Requested-With` CSRF guard doesn't help against script running in that origin. Any stored XSS in
  Forgejo, an extension or a code-server webview could call `/admin/api/forgejo-password/*` as the facilitator. No
  such XSS was found. The longer-term fix is a separate host for `/admin` (§3.2).
- **Low–Medium · Reported:** `ctf-controller/view.py:53` serves target content on the dojo origin with
  `script-src 'unsafe-inline'`. It is well contained (`connect-src 'none'`, `frame-src 'none'`, COOP, no `dojo_*`
  cookies forwarded), but `form-action 'self'` still allows same-origin form posts into other sinks. Serve ctf-view
  from its own port or origin, or drop `form-action 'self'`.
- **Low · Verified, corrected from the reviewer's Medium:** the start check doesn't count an *empty* password as weak
  (`engine/dojo/checks.py:13`), while `env-setup.sh`'s `is_weak` does. It isn't a bypass, because `check_login` never
  accepts an empty password (`accounts.py:67`), so the risk is a class that starts but nobody can log in to. Make
  `start` fail on empty required keys, as `doctor` already reports them. **[engine]**
- **Low · Reported:** the `--pass` gate code is stored in plain text in `.build-state/current.json` and
  `history.jsonl` (directory mode 755). `GATEWAY_GATE_TOKEN = sha256("dojo-gate:" + code)` is unsalted, so a short
  code can be brute-forced offline from the cookie. Record it as `--pass <redacted>` and make the token an HMAC
  keyed by `GATEWAY_TOKEN`. **[engine]**
- **Low · Reported:** the achievements `CLIENT_HASH` anti-tamper check
  (`modules/achievements/service/server.py:266-270`) hashes a file students can read, so it doesn't protect
  anything. The signed events with nonce and replay handling in `store.py` are what actually protect it; drop the
  hash or label it honestly.
- **Low · Reported:** the fake `ghp_…` teaching tokens (`workshops/vault-fundamentals/content/lab/lab1.md:42,149`,
  `content/bots/steps.sh:155`) look real enough to trip GitHub push protection or secret scanners. Rename them to
  `ghp_EXAMPLE…` or add a scanner allowlist.
- **Low · Reported:** `workshop.env`/`module.env` are run by `sh` with the full environment, including every
  secret. That's fine for packs in this repo; say in `workshops/README.md` that packs are trusted code.
- **Low · Reported:** the student terminal image installs `sudo`, `curl` and `wget`, which students don't need.
  Students have no sudo rights and no internet, so this is cosmetic.

### 1.7 Checked and sound
Reviewers specifically confirmed:
- **Gateway token:** compared with `compare_digest` first thing in `do_GET`/`do_POST`, and `header_up` replaces
  client values.
- **`/admin` gating:** done twice, by Caddy and by `refuse_non_facilitator`.
- **Cookies:** HMAC-signed and compared with `compare_digest`.
- **Workspace isolation:**
  - per-UID iptables rules over ports 9000-9899 and 7682;
  - ttyd and the watch session run as root and wrap `su`;
  - a tight open-redirect check (`local_path`).
- **Manifests:** strict regexes, fixed templates, and checks on upstreams and path overlaps.
- **CLI subprocesses:** no `shell=True` or `os.system` anywhere; `.env` is created with umask 077, and setup,
  migrate and maintain enforce mode 600.
- **Supply chain:** `boot.py` installs hash-pinned wheels with an atomic rename. Base images are pinned by digest and
  the downloaded tools are checked by sha256.
- **Brokers:** the SO_PEERCRED brokers and `ctf-notes`' dir-fd and `O_NOFOLLOW` handling.
- **Achievements:** the event path is HMAC-signed with nonce and timestamp.
- **Secrets in the repo:** none committed, and no real CTF flags in student content.

## 2. Reliability and performance

### 2.1 The PID-1 reaper races `subprocess`. Medium · Verified that the reaper exists; the race is reported
`engine/web-terminal/workspace-control.py:713-719` runs `os.waitpid(-1, 0)` in a thread. When it collects a child
before `subprocess.run`/`Popen.wait` does, Python sees ECHILD and reports **returncode 0**.

`list_sessions`, `_run_step` (resets) and `_nested_userns` branch on that exit code, so failures can pass as success.
How often this happens wasn't measured.

**Fix:** reap only orphans. Track the PIDs `subprocess` owns and skip them, or handle SIGCHLD and `waitpid` specific
PIDs. **[engine]**

### 2.2 Slow work under the global `running_lock`. Medium · Reported
`ensure_holder` busy-waits up to 5 s and `_nested_userns` forks `su` (5 s timeout), both inside `start_workspace`
while it holds the global lock. That stalls every other `/start`, `/stop` and reset during a class start-up burst.

**Fix:** hold the global lock only to update the dict, and give each user their own lock for namespace setup.
**[engine]**

### 2.3 Other items, all Reported
- **Medium:** on each `/status` cache miss (every 3 s while the roster is open), workspace-control spawns `pgrep`
  plus `su - user -c tmux list-sessions` per user, about 60-100 forks per poll at 30 students. Use one `ps` call or
  read the tmux sockets directly, and take `watchable` out of the roster poll. **[engine]**
- **Low:** `allocator/api.py:61-72`: a cold VS Code page load sends many asset requests, and each one makes its own
  blocking `POST /start` on a READY_CACHE miss. Have one request do the start and the others wait for it. **[engine]**
- **Low:** `engine/dojo/start.py` (compose `up`): on Ctrl-C, `proc.terminate()` is never waited on, so podman-compose
  can outlive the CLI. `stop` still recovers it.
- **Low:** `envfiles.resolve` runs `workshop.env` twice, before and after the modules. Every pack's shell runs twice,
  including any side effects and timeouts. A declarative `MODULES` would remove this (§3.4).
- **Low:** `stack.py:113-145` finds podman-compose's Python by reading its shebang, and runs `compose config` twice.
  That's fragile on other installs.
- **Low:** `boot.py`: `.complete` is the only integrity check after first install, and a failed rename leaves a raw
  traceback.
- **Medium–Low:** the `ctf-host` healthcheck waits on a hard-coded list of 13 images duplicated in `compose.yml` and
  `module.env`. The 10-minute retry budget is a symptom of that.
- **Low:** resets go through a single worker one at a time (up to 300 s per step), so a class-wide reset is slow.
  That's acceptable; just know it.

## 3. Architecture and design decisions

### 3.1 What's working well (keep it)
- **Engine, modules and workshops are kept separate.** The engine stays workshop-agnostic: manifests are rendered
  through fixed gate templates, and there are no per-workshop flags. This is the best decision in the repo. It is
  documented, enforced by the renderer, and has held up across 12 packs.
- **Caddy `forward_auth` is the only place identity is decided**, using a shared token the allocator checks again.
  Per-upstream HMAC tokens and stripping `X-Dojo-*` before the gate make a clean template.
- **Settings provenance.** `dojo.toml` → `dojo.local.toml` → `.env` → profiles, with an origin chain per key
  (`./dojo config <ws> KEY`). It works well, and the migration from the old layout was handled.
- **Chained terminal images** are labelled with a source hash and rebuilt only when their source changes, so the
  module and workshop layers compose cleanly.
- **Locking in the allocator** is documented and followed: no I/O under `_state_lock`, versioned slot saves, and
  small separate caches.
- **The dind box** (`internal` networks, socket groups 1900/1901, no published ports) for `ctf-host` and
  `cloud-host` is well reasoned. Neither socket is reachable by students.
- **Python CLI with hash-pinned wheels** rather than a growing shell script: typed errors, 146 fast tests, and shell
  kept only where it fits.

### 3.2 Sessions and origins
- **Stateless 12 h cookie, no revocation.** The cookie holds only the account name, and the student cookie is shared
  by the whole class. Add an epoch to the HMAC that `/logout` or a facilitator "sign everyone out" bumps, or use a
  random session id kept on the server. That would also limit the damage from §1.2.
- **Single origin.** Putting the facilitator workspace on its own host (for example `admin.<domain>`) would make the
  CSRF guard meaningful, and the facilitator's cookie would never reach student-influenced content. This is the
  structural fix behind §1.2 and §1.6's same-origin item. It's a big change, so do it only if the class becomes
  higher-stakes.
- **`resolve_identity` mixes two identity sources:** the facilitator comes from a header and students from
  `dojo_session`. Split it into two explicit functions so a handler can't pick the wrong one.
- **Record as an invariant:** `/admin/watch` and `/ide` pass the facilitator's own cookies to student-process ports.
  That's only safe because ttyd runs as root, which is another reason to strip cookies (§1.2).

### 3.3 Identity for terminal → module calls (the main design gap)
- **Two strong patterns exist:**
  - gateway token plus `X-Auth-User` for browser calls;
  - a root SO_PEERCRED broker for terminal calls (dojo-cloud, openbao, ctf-notes).
- **The problem:** `ctf-flags`, `ctf-checker` and `dojo check` → achievements use a self-asserted `$USER` instead.
  Each module chose its own approach, and §1.1 is the result.
- **Proposal:** one shared terminal-side identity broker, for example `/run/dojo/identity.sock`, that issues a
  short-lived signed token tied to the caller's uid. Every module CLI sends that token, and every service checks it
  with one `_shared` helper. The `dojo` command plug-in system (`cmd.d`) is a natural home for the client side.
- **Related:** per-user secrets are derived as HMAC(`STUDENT_PASSWORD_SEED`, label) in at least five places (flags,
  `dns_key`, cloud `client_secret`, the openbao broker, tokens), each a copy kept in step by a parity test. Add
  `derive(seed, label, user)` to `_shared` with a registry of labels.

### 3.4 Make pack metadata declarative
- **Today:** `workshop.env` is shell (with `$(printf … | sha256sum)` and similar). That couples checking a pack to
  running it, forces the two-pass resolve (§2.3), and means `list`, `validate` and `stop` must run pack code just to
  read `MODULES`.
- **Alternative:** a `workshop.toml` (matching `dojo.toml`) holding static keys and `modules = [...]`, with computed
  values moved to a small hook or into the CLI. That would allow static validation, a `./dojo validate <pack>`, and no
  double sourcing.
- **Small mismatch:** `validate.py:41` checks syntax with `bash -n`, but the file is run with `sh`.

### 3.5 ctf-range has outgrown "module"
- **Size:** 13 services, more than 10 targets, a 367-line `ctf-host` Dockerfile and about 19k lines. It is a product
  inside a module.
- **Option:** split it into `ctf-range-core` (host, controller, checker, builder, flags, view, notes), with targets as
  plug-ins (a `targets/<name>/` contract that packs select).
- **Layout duplication:** the port base and stride, attack-IP layout and expected image list are repeated in
  `module.env`, `compose.yml`, `controller.py`, `checker.py`, `50-ctf-range.sh`, `view.py` and `bot.py`. Only
  "must agree with" comments keep them in step. Use one computed layout module plus a parity test.

### 3.6 Achievements: pack logic lives in the module
- **Today:** `modules/achievements` is about 15k lines and holds per-workshop tests and logic (`test_certs_pack`,
  `test_vault_pack`, `test_tofu_pack`, …).
- **Alternative:** have workshops ship their catalog and plugin under `workshops/<name>/achievements/`, with the
  module acting as a loader. That keeps workshop logic out of a shared module, which is the same rule the engine
  already follows.

### 3.7 Module service images
- **Today:** feedback, achievements, openbao and runner-pool reuse `gitopsdojo/allocator:local` with source
  bind-mounted read-only from the live tree.
- **Trade-off:** there's no build step, but a module can't be versioned or hash-pinned on its own, and allocator
  changes silently become module runtime changes.
- **Option:** a small `gitopsdojo/module-runtime` base image, or `COPY` the source into module images.

### 3.8 `workspace-control.py` does too much
One 850-line PID-1 process handles supervision, namespaces, resets and status. Splitting out a proper subreaper
(§2.1) and giving each user a lock (§2.2) are the two changes that matter. The rest can stay.

## 4. Duplication, code quality and testing

### Duplication to collapse (most in `modules/_shared`)
- **`flags.py`:** three copies, in ctf-flags, ctf-controller and the ctf-checker image. Move it to `_shared/flags.py`.
- **HTTP handlers:**
  - Hand-written `http.server` handlers each re-implement `_json`, body limits, `log_message` and `ThreadingMixIn`:
    17 `log_message` overrides, 6 `ThreadingMixIn`, 6 `_json`.
  - `ctf-flags/service.py:67-76` and `ctf-controller/controller.py:760-770` send no `SECURITY_HEADERS`.
  - A `_shared` base handler (auth, JSON, body reader, 413) would remove about 300 lines and make the headers
    consistent.
- **Bearer-token checks** are re-implemented four times (`checker.py`, `controller.py`, `builder.py`,
  `dns-gate/gate.py:446`). Use `dojo_http.token_ok`.
- **Facilitator username default:** `ctf-range/compose.yml:247,322` defaults `FACILITATOR_USERNAME` to `admin`,
  every other module to `root`, and `controller.py:251` to empty. It's repeated about 15 times. Have the engine always
  export it, or use one helper.
- **`dojo_secret.py`** is copied to three places, kept in step only by a test.
- **CTF portal source:** ctf-defend holds three copies of customer-portal (`content/sample-repo/`,
  `content/sample-repos/customer-portal/`, `modules/ctf-range/targets/customer-portal/`). leaky-config and
  policy-bypass are also duplicated between `sample-repos/` and `targets/`. Keep one source and copy it at build
  time, as `SHARED=` already does.
- **`check-pins-sync.sh`:** three differing copies (ctf-defend, cloud-policy-as-code, dojo-introduction). Make one
  shared script in `workshops/assets/`.
- **CTF pack settings:** the four ctf-* packs share a near-identical `workshop.env` block (`STUDENT_COUNT`,
  `CTF_CONTROL_TOKEN`, `CTF_HOST_*`…). Put it in module defaults or a shared include.

### Code structure
- **Big CLI files:** `engine/dojo/cli.py` (854 lines), `start.py` (786) and `build.py` (400). `start.py` mixes option
  parsing, safety checks, build planning, compose orchestration and monitoring; split it along those lines.
- **Allocator routing:** `allocator/handler.py`'s `do_GET`/`do_POST` are long if-chains. A route table with a
  per-route auth level (`public`, `session`, `facilitator`, `csrf`) would make the `X-Requested-With` checks
  consistent; today they are repeated three times in `do_POST`.
- **`api.py:91-151`:** `handle_route_check` computes `denied`, then re-checks each condition. Do it in one pass.
- **Comments that disagree with the code:** the `LoginGuard` docstring (§1.3), and `render_extensions.py`'s "no raw
  values" comment, while `Cookie`, `Host` and `Authorization` are handled case by case.
- **Audit IDs** (`FIND-16`, `T1.1c`) in comments only make sense with the archive open. Add a one-line gloss when
  touching them.

### Testing gaps
- **No gateway config test.** A Caddyfile lint could parse the rendered config and check that every
  `reverse_proxy allocator` block sets the token and strips client identity headers (and, after §1.2, cookies). This
  is the cheapest way to stop trust-boundary regressions.
- **Untested engine pieces:** `workspace-control.py`, `entrypoint.sh` and `provision-account.sh` (the reaper,
  iptables order, namespaces).
- **Untested in modules:** ctf-checker identity, the ctf-flags HTTP handler, and the terminal firewall hook.
- **CLI modules with no test file of their own:** `boot.py`, `doctor.py`, `monitor.py`, `backup.py`, `logs.py`,
  `validate.py`. No test covers the empty-password or `--pass` redaction cases.
- **Strong coverage:** achievements, dojo-cloud, `_shared/test_dojo_http.py`, and the allocator's roughly 2,000
  lines of tests.
- **Noisy test output:** CLI tests print live "Tearing down…" lines. A quiet console fixture would remove the
  noise.

### New finding: 20 students exhaust the terminal container's pids cap (High for capacity)
- **What happened:** with 20 bots, the terminal container reached **1009 of 1024 pids**.
  - `podman exec` failed with `crun: fork: Resource temporarily unavailable`.
  - workspace-control's log filled with `RuntimeError: can't start new thread`.
  - None of the 20 bots finished round 1 within about 15 minutes.
- **Where the cap comes from:**
  - `workshops/cloud-policy-as-code/workshop.env:28` sets `WEB_TERMINAL_PIDS_LIMIT=1024`; its comment says "1024
    covers a class of 20". In practice 20 students plus the platform's own processes fill it.
  - `./dojo config` shows that value overriding both `dojo.toml` (2048) and this machine's `dojo.local.toml`.
- **Two problems:**
  1. **The number is too small.** One `tofu apply` is about 25–30 threads, and each student also runs a shell, a
     multiplexer and the `dojo` tooling.
  2. **A workshop file overrides the operator's capacity sizing.** The pack can't know the machine or the class
     size, but its fixed value beats `./dojo capacity --students N` and `dojo.local.toml`. This is the
     "workshop/module values override the operator" layering noted in §2.3.
- **Fix:**
  - Have the workshop state a per-student need instead of a total (for example `PIDS_PER_STUDENT=60`), and let
    `./dojo` compute `max(operator value, STUDENT_COUNT × per-student + base)`.
  - Or treat workshop values as a minimum that never lowers the operator's setting. **[engine]** for the layering
    rule.
  - Also have the start warn when the cap is below students × per-student.
- **Follow-up:** re-run at 20 with the cap raised (for example 2048) to find the real per-student figure. That feeds
  P9, the load test.

### §2.1 reaper race: Confirmed
- **The reaper runs:** `reap_children` is started as a daemon thread (`workspace-control.py:844`).
  workspace-control is PID 2 under `podman-init`, so it isn't PID 1, but its `os.waitpid(-1, 0)` still collects
  every child.
- **Reproduction:** the same loop, run inside the live terminal container (Python 3.11.2): **26 of 500**
  `subprocess.run(['false'])` calls returned **0 instead of 1**, about 5%, under heavy load.
- **What it means:** a failed `tmux list-sessions`, reset step or `su` setup can look successful about 1 time in
  20 under load. Fix as in §2.1. **[engine]**

### §1.2 cookie leak: real, but low impact in this workshop
- **Confirmed in code:** `render_extensions.py` `caddy_for_route` (about lines 345–385) removes `Authorization`
  and sets the identity headers, but never touches `Cookie`. Caddy passes `Cookie` through by default, so
  `dojo_login` and `dojo_session` reach every extension upstream.
- **Not captured live:** no upstream in this workshop echoes request headers, and the gateway log hides cookies.
- **Routes checked:**

  | Route | Upstream | Gate |
  |-------|----------|------|
  | `/cloud` | cloud-api | identity |
  | `/runners` | runner-controller | facilitator |
  | `/sensei-admin` | sensei | facilitator |
  | `/feedback` | feedback | identity |
  | `/feedback-admin` | feedback | facilitator |

  - All of these are platform code. None serves content students write, and the student-deployed resources in
    `cloud-host` have no gateway route.
  - Not checked: whether `/runners` or `/cloud` show student-supplied output. Rendering is covered in P3/P6.
- **Revised severity:** Low today, but it becomes Medium the moment any route proxies student-built content, for
  example a "preview my deployed app" route. The cookie strip is still worth doing as cheap insurance.
  **[engine]**
- **Still open:** whether a student uid could bind the facilitator-reachable `/admin/watch` and `/ide` ports. ttyd
  and code-server weren't running under zellij, so this wasn't checked. It goes to P4.

### §2.2 lock stall at class start: Not measured
- **zellij flavor:** this machine runs `flavor = "zellij"`, so code-server workspace starts (the code path in

- **No timings:** workspace-control and the allocator logged no per-student start timestamps (0 `"event"` lines),

- **To measure:** run with a `dojo.local.toml` profile that sets `[terminal] flavor = "code-server"`, plus one audit line per

### Bad
1. **The CTF control token is committed, and student CI can reach the controller.** High in ctf-trust-chain;
   latent in ctf-access, ctf-server-trust and ctf-secrets-config. · Partly verified.
   - **The token:** `CTF_CONTROL_TOKEN=dev-ctf-control-token-<pack>` is a constant in the workshop.env of those four
     packs. Anyone who has seen the repo knows it.
   - **What it unlocks:** `ctf-controller` `POST /redeploy` and `/reconcile` and `GET /slots` and `/schedule`
     (`modules/ctf-range/ctf-controller/controller.py:786-960`). These take `user` from the body, so the token holder
     can redeploy any student's slot.
   - **Reachability (I checked this):**
     - **From a terminal: blocked, but by accident.** ctf-controller is on `workshop_lab` at port 9000, and the
       engine's terminal firewall drops student traffic to *any* destination on ports 9000–9099
       (`engine/web-terminal/entrypoint.sh:254`). That rule exists to protect the IDE ports, so the controller is
       safe only because it happens to share that port range. Moving it to, say, 9300 would expose it.
     - **From CI: open.** ctf-trust-chain (and ctf-defend) load `runner-pool`, and student jobs on `runner_net`
       reach `ctf-controller:9000` directly. That firewall rule doesn't apply there.
   - **Fix:** derive the token per run from `GATEWAY_TOKEN`, as ctf-defend does (`printf … | sha256sum`), and never
     commit a default. Long term, use per-user tokens (§1.4).
   - **Live check needed:** curl the controller from a CI job in ctf-trust-chain and from a terminal. Goes to P4.
2. **ctf-defend gives the control and build tokens to students' CI.** High · Reported; this confirms §1.4.
   - **The leak:** `workshops/ctf-defend/compose/terminal/start.d/90-ctf-defend.sh:141` writes `CTF_BUILD_TOKEN` and
     `CTF_CONTROL_TOKEN` as Actions secrets in every student repo. A student edits the PR workflow to print them.
   - **What it unlocks:**
     - controller `/redeploy` for any classmate;
     - checker `/gate` (`modules/ctf-range/ctf-checker/checker.py:366`) with any `user`;
     - builder `POST /build` (`modules/ctf-range/ctf-builder/builder.py:187`) for any user's slot.
   - **Fix:** use Forgejo's Actions OIDC job token, which already works in this repo: `dns-gate` and vault's
     `app-host /deploy` verify it. Have the pipeline present its OIDC token and have the controller, checker and
     builder take the user from the verified `repo` claim instead of the body.

### Port squatting lets a student take over another user's IDE or terminal, including the facilitator's. High · Confirmed live and in code
- **What a student can do:** student01 successfully bound `0.0.0.0` on another student's IDE port (9002), the
  facilitator's IDE port (9099) and terminal port (9599), and others (9010, 9502, 9510). The gateway could then reach
  student01's listener on each: `wget http://web-terminal-ingress:9002/`, `:9099/` and `:9599/` all returned
  student01's `http.server` directory listing.
- **Why nothing stops it:**
  - The terminal firewall (`DOJO_ISOLATION`) only filters outgoing *connections*; it can't stop a *bind*.
  - The incoming rule accepts anything on the ingress interface.
  - Readiness is just "can root connect to the port": `port_open()` at `engine/web-terminal/workspace-control.py:411-414`,
    used at lines 560 and 805. A squatter's listener therefore counts as "ready", and the allocator hands the
    gateway that port.
- **Attack:**
  1. Before the facilitator (or a classmate) opens VS Code or the terminal, the student starts a listener on that
     person's port.
  2. The workspace's real code-server or ttyd can't bind, and the readiness check passes anyway.
  3. The gateway proxies the victim's `/ide`, `/term` or `/admin` workspace traffic to the student, with every
     browser cookie attached, because cookies aren't stripped (§1.2).
- **Outcome:** a student who catches the facilitator's `dojo_login` cookie has 12 h of full facilitator access.
  They can also show a fake IDE or terminal page to anyone.
- **Not yet tested:** a real browser request through Caddy carrying cookies. The parts of the chain were each shown
  separately (the bind, gateway reachability, and readiness by connect), and they fit together.
- **Fix, best first.** All need your go-ahead. **[engine]**
  1. **Check who owns the listener before reporting ready.** In `port_open`/`/auth-check`, look up the listening
     socket in `/proc/net/tcp` and require its uid to be the workspace owner's. Refuse otherwise, kill the
     squatter's process and log it to audit. This closes most of the hole cheaply.
  2. **Sweep regularly:** every few seconds, kill any listener on 9000–9899 or 7682 owned by the wrong uid. This
     covers the window after a workspace exits.

   - **Who it affects:** only classes run from this machine; the shipped default is 2048. But `--env home` and

     for the check.
2. **cloud-policy-as-code's workshop.env sets the terminal's limits** (`WEB_TERMINAL_PIDS_LIMIT=1024`, memory
   `6g`) and is the only pack that does. Medium. Its 1024 is still too small for 20 (P1). It also overrides the
   operator's sizing in both directions. The fix is in P1: the workshop states a per-student need and the CLI
   computes the total.
3. **vault-fundamentals app-host joins students' network to the CI network.** Medium.

   - **Fix:** drop `NET_ADMIN` and `SETPCAP` unless they're used. Consider splitting the student-facing proxy from

4. **Privileged nested-container hosts:** Medium; accepted by design, worth recording.
