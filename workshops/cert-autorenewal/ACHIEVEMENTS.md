# cert-autorenewal: achievements catalog

Generated from `achievements/` beside this file by `modules/achievements/catalog/render_md.py`. Do not edit this file: edit the JSON and run the script (a unit test fails when this copy is stale).

**How to read it.** Points are the defaults (milestone 10, funny 0, challenge 100, capstone 300, all settable in
`.env`). `core` means the milestone counts toward the certificate (80% of the `core` set). Triggers (the *When*
column) name where the event comes from:

- `shell:` the student ran this command and it exited as stated (shell hook; the command and the branch are logged)
- `forgejo:` a Forgejo webhook event for that student
- `dns:`, `ca:`, `cloud:`, `bao:` an audit or activity line from that service, read by the module that owns it
- `verify:` the achievements service checks the end state (verifiers, run by `dojo-check` or after an event)

`{user}` is the student's login (`student07`). Jokes are the toast text.

**Funny unlocks are worth nothing on purpose.** They never move the score; a student sees each one they earned, and
what they did to earn it, in their own "Moments" table on the landing page. Cheating is the only thing that subtracts
(at most 1 point).

**Every lab is mandatory**, so every lab milestone is `core`. Challenges, the capstone and the funny unlocks are
bonuses and never count toward completion. The shared cheating and "bumped into your neighbour" unlocks live with the
module, not in a workshop.

**Where challenges run.** The shared pieces are the CA (`step-ca`), `demo-app` and the `certs.dojo.test` zone. A challenge changes only the student's own vhost directory (`/srv/webroot/{user}/`) and names under `{user}.certs.dojo.test`, which is exactly what the DNS gate's per-student key already allows. No challenge reconfigures the CA, nginx or the zone's shared records. The student's hostname is `{user}.certs.dojo.test`. Triggers here: `shell:`, `verify:` (end state on `demo-app` or the CA), `ca:` (CA log), `dns:` (dns-gate lines).

## Rules for challenges and capstones (apply to every workshop)

Students share one Forgejo, one DNS server, one CA, one cloud and one vault, so a challenge that changes shared state
breaks for the second person to try it. Every challenge and capstone must follow these:

1. **Write only to a space keyed on `{user}`:** their own repo, zone, namespace, slot or name prefix. Never `main` of a
   shared repo, a shared zone's apex, or an unprefixed name.
2. **Verify only that space.** Assertions read `{user}`-keyed state, never global state (a shared `main`, a whole zone,
   "the cloud is empty"), so another student's work can neither pass nor fail yours.
3. **No dependency on another student.** No peer approval, no "wait for a classmate". If a review or a merge is part of
   the goal, the seed provides the other party (a seeded PR from a bot account), or the facilitator, and only where
   truly required (the catalog says so).
4. **Change no shared config:** CA lifetimes, quotas, policies, branch protection and shared zones are read-only to a challenge.
5. **Seed per student.** The service creates one seed for each student (a repo, a branch set, a zone file) when the
   challenge is first opened. It is never one shared seed with a per-student label, because a fix to it lands for everyone.
6. **Independent of each other.** A challenge must still pass if another challenge was never attempted, or was undone
   (a pass is recorded when it is checked, and later clean-up never undoes it).

The catalog validator enforces what it can: every challenge declares a `space` containing `{user}`, and every
structured `verify` assertion mentions `{user}`.

## Challenges (100 points, optional, no steps given)

Each has two hints (25% each by default) and an answer that scores zero. The check is by outcome, so any way of doing it counts.

At open, the service seeds one wildcard A record `*.{user}.certs.dojo.test` to `demo-app` (through the DNS gate, in the
student's own scope), so any new hostname the challenge needs already resolves. Verifiers read the student's own
vhost directory and the certificate `demo-app` serves for their own hostnames only.

### C1: The Second Site (after Lab 2 or 3)

- **Points:** 100
- **Where it runs:** the student's own vhost directory `/srv/webroot/{user}/` and names under `{user}.certs.dojo.test`
- **Goal shown to the student:** Give `shop.{user}.certs.dojo.test` its own trusted certificate, using either tool, without touching the first site.
- **Seed:** `dojo-challenge start c1` creates `{user}/cert-shop` (owned by the student, cloned to `~/lab/cert-shop`): a brief and `shop.conf`, a port-80 vhost for `shop.{user}.certs.dojo.test` with its own webroot folder. The wildcard A record `*.{user}.certs.dojo.test` (made for every student by the DNS seed at stack start, pointing at `demo-app`) is what makes the name resolve.
- **Verify:** `demo-app`'s HTTPS listener serves `shop.{user}.certs.dojo.test` (checked over SNI) a certificate that chains to the CA root, matches the name and is not expired, and is not the certificate served for `{user}.certs.dojo.test`. It cannot see whether the first site's serial changed, only that the two sites hold different certificates. And `shop.conf` on `main` of `{user}/cert-shop` names `shop.{user}.certs.dojo.test` and has a `listen 443 ssl` block (push the vhost you run). The repo's whole history (every branch, every commit) holds no private key.
- **Hint 1:** Same steps as your first site, new hostname.
- **Hint 2:** New vhost, new issuance, new install.
- **Answer:** `dojo-challenge start c1`, copy `shop.conf` into `/srv/webroot/{user}/conf.d/` and make `shop-html`, issue for `shop.{user}.certs.dojo.test` with certbot (Lab 2) or acme.sh (Lab 3) into a folder of its own, add a `listen 443 ssl` block pointing at that certificate, copy it in again, push `shop.conf` to `main` (no key in the repo), and run `dojo-check c1`.
- **Collision check:** a second vhost in the student's own subdirectory and the student's own repo `{user}/cert-shop`; issuance goes through the shared CA, which handles concurrent orders for different names. The check reads only names under `{user}.certs.dojo.test` and that repo.

### C2: The Short Fuse (after Lab 4)

- **Points:** 100
- **Where it runs:** the student's own vhost directory `/srv/webroot/{user}/` and names under `{user}.certs.dojo.test`
- **Goal shown to the student:** Certificates from this CA only last 5-10 minutes. Make `{user}.certs.dojo.test` renew on its own and stay valid for 20 minutes without you touching it.
- **Seed:** `dojo-challenge start c2` creates `{user}/cert-fuse` (cloned to `~/lab/cert-fuse`): a brief, Lab 4's `renew-and-reload.sh` with the student's name filled in, and a `renew.cron` holding only comments.
- **Verify:** the first `dojo-check c2` starts a 20-minute watch, and the service then looks at `{user}.certs.dojo.test` on its own every sweep (about 20 s): every look must find a valid certificate, and the served serial must change at least twice before the 20 minutes are up. A look with no valid certificate starts the watch again; so does a restart of the achievements service. A lapse shorter than one sweep can be missed. Once the watch passes, `renew.cron` on `main` of `{user}/cert-fuse` must hold an active line (not only comments). The repo's whole history (every branch, every commit) holds no private key. The repo is read only after the watch passes, so watching costs Forgejo nothing.
- **Hint 1:** Cron runs at most once a minute.
- **Hint 2:** `renew` only acts when the cert is close to expiry.
- **Answer:** `dojo-challenge start c2`, pick the client's block in `renew-and-reload.sh`, put Lab 4's every-minute line in `renew.cron` and install it (`crontab renew.cron`), push both to `main`, run `dojo-check c2` once to start the watch, and leave it alone for 20 minutes (the cert must be reissued at least twice). The challenge clears on its own; `dojo-check c2` shows how far the watch has got.
- **Collision check:** the student's own vhost directory, hostname and repo `{user}/cert-fuse` only.

### C3: Members Only (after Lab 2 or 3)

- **Points:** 100
- **Where it runs:** the student's own vhost directory `/srv/webroot/{user}/` and names under `{user}.certs.dojo.test`
- **Goal shown to the student:** Serve `https://members.{user}.certs.dojo.test` only to clients that present a certificate from the lab CA (mutual TLS); everyone else is refused.
- **Seed:** `dojo-challenge start c3` creates `{user}/cert-members` (owned by the student, cloned to `~/lab/cert-members`): a brief and `members.conf`, whose port-80 block is done (http-01 from `members-html`, a redirect for the rest) and whose HTTPS block is commented out with `TODO`s for the certificate, `ssl_client_certificate` and `ssl_verify_client`. The wildcard A record `*.{user}.certs.dojo.test` makes the name resolve.
- **Verify:** `members.{user}.certs.dojo.test` is served (over SNI) a valid certificate for its own name. Without a client certificate, `https://members...` is refused (the handshake fails, or nginx answers 400, 401, 403, 495 or 496). With the checker's own client certificate, which step-ca issues at start from the lab CA's intermediate, it answers 2xx. `members.conf` on `main` of `{user}/cert-members` has an uncommented `ssl_verify_client on`. The repo's whole history (every branch, every commit) holds no private key. Not checked: that a certificate from another CA is refused (a client certificate that doesn't verify gets 400 from nginx anyway).
- **Hint 1:** The server already trusts the CA for its own certificate; it needs telling to trust it for clients too.
- **Hint 2:** Any certificate from the lab CA is also a client certificate, until it expires.
- **Answer:** `dojo-challenge start c3`; make `members-html` with a page and copy `members.conf` in; issue for `members.{user}.certs.dojo.test` with `-w /srv/webroot/{user}/members-html` and copy it into `certs/` (e.g. `members-fullchain.pem`, `members-privkey.pem`); copy `/opt/step-ca-root/root_ca.crt` into `certs/`; in the HTTPS block set the two certificate lines, `ssl_client_certificate /srv/webroot/{user}/certs/root_ca.crt;` and `ssl_verify_client on;`, uncomment it and copy it in; test with `curl --cert`/`--key` (a fresh certificate from the lab CA, e.g. the members one); push `members.conf` to `main` (no key); `dojo-check c3`.
- **Collision check:** a vhost in the student's own subdirectory and the student's own repo `{user}/cert-members`; the check reads only names under `{user}.certs.dojo.test` and that repo, and presents a client certificate only to that name.

## Capstone (300 points, optional): The Wildcard Heist (a friendly one)

- **Points:** 300
- **Where it runs:** the student's own vhost directory `/srv/webroot/{user}/` and names under `{user}.certs.dojo.test`
- **Goal shown to the student:** Issue a wildcard certificate for `*.{user}.certs.dojo.test` using dns-01, install it on two different vhosts (`www` and `api` under your name), and set up renewal that works for both. Then make HTTPS the only way in: plain HTTP redirects to HTTPS permanently, and HTTPS sends HSTS. And harden the API: `api` also sends `X-Content-Type-Options: nosniff` and a `Content-Security-Policy`.
- **Seed:** `dojo-challenge start capstone` creates `{user}/cert-heist` (cloned to `~/lab/cert-heist`): a brief, port-80 vhosts `www.conf` and `api.conf`, a `dns-hook.sh` skeleton for certbot's `--manual-auth-hook` (its body is the student's), and a `renew.cron` holding only comments. The wildcard A record `*.{user}.certs.dojo.test` (made by the DNS seed at stack start) makes `www` and `api` resolve. The TXT record goes through `dns-api` with the student's own key, so `_acme-challenge.{user}.certs.dojo.test` is theirs alone.
- **Verify:** `www.{user}.certs.dojo.test` and `api.{user}.certs.dojo.test` are both served, over SNI, a valid certificate that chains to the CA root, that covers `*.{user}.certs.dojo.test`, with the same serial on both. Plain `http://` for each answers a permanent redirect (301 or 308) to the same name over `https://`, and each HTTPS response carries `Strict-Transport-Security` with `max-age` of at least 86400. `https://api...` also answers with `X-Content-Type-Options: nosniff` and a `Content-Security-Policy` that sets `default-src`. On `main` of `{user}/cert-heist`: `www.conf` and `api.conf` each have an uncommented `listen 443 ssl` and `ssl_certificate` lines no longer `TODO`, and `renew.cron` holds an active line. The repo's whole history (every branch, every commit) holds no private key. Not checked: that a forced renewal really updates both sites; `includeSubDomains`/`preload` (not wanted on a lab name); what the CSP allows; the TLS protocol versions (on demo-app's shared port 443 nginx takes them from the default server, so no single site can set them).
- **Hint 1:** A wildcard only works through DNS.
- **Hint 2:** One cert file, two vhosts, one reload; each header is one `add_header ... always;` line.
- **Answer:** `dojo-challenge start capstone`; write `dns-hook.sh` (Lab 5's PATCH with `$CERTBOT_VALIDATION`, then wait for `dig`); `certbot certonly --manual --preferred-challenges dns-01 --manual-auth-hook "sh $HOME/lab/cert-heist/dns-hook.sh" -d '*.{user}.certs.dojo.test'` (or acme.sh); copy the one certificate into `/srv/webroot/{user}/certs/`; in `www.conf` and `api.conf` uncomment the HTTPS block, point both certificate lines at it and add `add_header Strict-Transport-Security "max-age=86400" always;`, in `api.conf` also `add_header X-Content-Type-Options nosniff always;` and `add_header Content-Security-Policy "default-src 'none'; frame-ancestors 'none'" always;`, and make the port-80 block `return 301 https://$host$request_uri;`; copy them in; a `renew.cron` line for `certbot renew --no-random-sleep-on-renew` (the hook makes it unattended), installed; push it all to `main` (no key); `dojo-check capstone`.
- **Collision check:** the challenge TXT name is under the student's own parent, so two students issuing at once never overwrite each other's record; the repo is the student's own `{user}/cert-heist`.
- **Badge tier:** capstone (stars)
