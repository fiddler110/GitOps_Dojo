# cloud-policy-as-code: achievements catalog

Generated from `achievements/` beside this file by `modules/achievements/catalog/render_md.py`. Do not edit this file: edit the JSON and run the script (a unit test fails when this copy is stale).

**How to read it.** Points are the defaults (milestone 10, funny 0, challenge 100, capstone 300, all settable in
`.env`). `core` means the milestone counts toward the certificate (80% of the `core` set). Triggers (the *When*
column) name where the event comes from:

- `shell:` the student ran this command and it exited as stated (shell hook; the command and the branch are logged)
- `forgejo:` a Forgejo webhook event for that student
- `dns:`, `ca:`, `cloud:`, `bao:` an audit or activity line from that service, read by the module that owns it
- `verify:` the achievements service checks the end state (verifiers, run by `dojo-check` or after an event)

`{user}` is the student's login (`student07`). Jokes are the toast text.

**Funny unlocks are worth nothing on purpose.** They never move the score; a student sees each one they earned, and
what they did to earn it, in their own "Moments" table on the landing page. Cheating is the only thing that subtracts
(at most 1 point).

**Every lab is mandatory**, so every lab milestone is `core`. Challenges, the capstone and the funny unlocks are
bonuses and never count toward completion. The shared cheating and "bumped into your neighbour" unlocks live with the
module, not in a workshop.

**Where challenges run.** Each student has a private Dojo Cloud subscription ("nobody else can touch yours"), so policy objects, compliance and resources are already isolated: a definition, assignment or exemption written by one student can never refuse, exempt or audit a classmate's resource. Nothing in a challenge or the capstone is shared: no platform-scope assignment (the built-in guardrails are read-only), no branch protection or other Forgejo settings, and no shared runner configuration (CI runs on runner-pool's single-use runners, for the student's own fork only). Inside one subscription a challenge still stays out of the labs' way: it works in a resource group of its own (`rg-{user}-c1`, `rg-{user}-c2`), assigns at that resource group's scope only, and keeps its own state in its own repo. Triggers here: `shell:` (conftest and opa in the terminal), `cloud:` (what cloud-api reports: refusals, policy writes, the portal's enforcement switch), `forgejo:` (fork, pull requests, pushes) and `verify:` (`cloud_policy`, `cloud_containers`, `ci_run`, `tree_file_contains`, `file_contains`, `pr_exists`).

## Rules for challenges and capstones (apply to every workshop)

Students share one Forgejo, one DNS server, one CA, one cloud and one vault, so a challenge that changes shared state
breaks for the second person to try it. Every challenge and capstone must follow these:

1. **Write only to a space keyed on `{user}`:** their own repo, zone, namespace, slot or name prefix. Never `main` of a
   shared repo, a shared zone's apex, or an unprefixed name.
2. **Verify only that space.** Assertions read `{user}`-keyed state, never global state (a shared `main`, a whole zone,
   "the cloud is empty"), so another student's work can neither pass nor fail yours.
3. **No dependency on another student.** No peer approval, no "wait for a classmate". If a review or a merge is part of
   the goal, the seed provides the other party (a seeded PR from a bot account), or the facilitator, and only where
   truly required (the catalog says so).
4. **Change no shared config:** CA lifetimes, quotas, policies, branch protection and shared zones are read-only to a challenge.
5. **Seed per student.** The service creates one seed for each student (a repo, a branch set, a zone file) when the
   challenge is first opened. It is never one shared seed with a per-student label, because a fix to it lands for everyone.
6. **Independent of each other.** A challenge must still pass if another challenge was never attempted, or was undone
   (a pass is recorded when it is checked, and later clean-up never undoes it).

The catalog validator enforces what it can: every challenge declares a `space` containing `{user}`, and every
structured `verify` assertion mentions `{user}`.

## Challenges (100 points, optional, no steps given)

Each has two hints (25% each by default) and an answer that scores zero. The check is by outcome, so any way of doing it counts.

Each challenge starts in a repo of its own (`dojo-challenge start cN` creates `{user}/challenge-cN` and clones it to `~/lab/challenge-cN`, with its own OpenTofu state `challenge-cN`), so it never changes the fork or the labs' policy state. Everything it creates lives in its own resource group and is assigned at that scope only, and the checks look only at those, so the labs' assignments never fail a check. A pass is recorded when checked; destroying it afterwards does not undo it.

### C1: Allowed Environments (after Lab 5 (parameters); one resource group, no container group)

- **Points:** 100
- **Where it runs:** the student's own Dojo Cloud subscription (`{user}`), its resource group `rg-{user}-c1` (the only assignment scope), and their own repo `{user}/challenge-c1` (cloned to `~/lab/challenge-c1`, local state)
- **Goal shown to the student:** Write a parameterised `audit` definition that flags any resource whose `env` tag is not in the array parameter `allowedEnvs`, assign it at the scope of `rg-{user}-c1` only with `allowedEnvs = ["dev", "test"]`, and see the seeded group (tagged `env = "sandbox"`) reported non-compliant.
- **Constraints:** Assign at the resource group's scope, never the subscription: the lab's own assignments must not change. The effect is the literal `audit`, so nothing is refused.
- **Seed:** `dojo-challenge start c1` creates `{user}/challenge-c1` (owned by the student, cloned to `~/lab/challenge-c1`): a `main.tf` with the resource group `rg-{user}-c1` tagged `env = "sandbox"` and two TODOs, a starter `rules/allowed-envs.json` full of `TODO`s, provider files with local state, and a README with the brief.
- **Verify:** Dojo Cloud Policy (the student's own subscription, read-only): an assignment whose scope is `rg-{user}-c1`, in enforcement mode `Default`, whose definition has the literal effect `audit`, declares the parameter `allowedEnvs` and whose rule mentions `tags['env']`, lists `rg-{user}-c1` as non-compliant; and `main.tf` on `main` of `{user}/challenge-c1` declares an `azurerm_resource_group_policy_assignment` (push it). Not checked: the exact parameter value.
- **Hint 1:** Lab 5's allowed-images rule already compares a field with an array parameter.
- **Hint 2:** `notIn` with "[parameters('allowedEnvs')]", and the assignment's `parameters = jsonencode({ allowedEnvs = { value = [...] } })`.
- **Answer:** `dojo-challenge start c1`, `cd ~/lab/challenge-c1`. Rule: `{"if": {"field": "tags['env']", "notIn": "[parameters('allowedEnvs')]"}, "then": {"effect": "audit"}}`.
